# ADR-002：兼容 V5 HTTP 边界而非全部查询能力

状态：Proposed  
日期：2026-07-31  
关联里程碑：M0、M1、M4、M6

## 背景

`POST /api/v5/query_range` 同时被 Explorer、Dashboard、Services 和 threshold rule 使用。直接创建新的公开端点会扩大前后端迁移范围；直接声称完整兼容 V5，又会迫使新引擎保留所有旧查询类型和高级字段。

## 决策

保留以下外部边界：

- `POST /api/v5/query_range` 路由。
- 身份认证、组织上下文和时间范围基本语义。
- `raw`、`trace`、`time_series`、`scalar` 请求/结果类型。
- 当前 V5 统一响应结构和错误响应形式。

只兼容能够转换为 Lite Query IR 的请求子集。旧高级字段或 query type 返回稳定的 unsupported error，不静默忽略、不尝试近似执行。

迁移期的新旧 engine 选择通过内部配置或测试机制完成，不加入公开请求协议。

## 备选方案

### 新建 `/api/v6/query_range`

第一阶段不采用。它会要求所有消费者一次性迁移，并在较长时间内维护两套公开协议。若 M1 证明 V5 envelope 无法清晰表达 Lite IR，再用新的 ADR 重新评估。

### 完整兼容 V5 请求

不采用。等同于重新实现被明确排除的能力。

### 接受字段但忽略不支持部分

不采用。查询可能成功返回语义错误的数据，对告警尤其危险。

## 影响

- 现有调用者可以逐步迁移，不需要同时修改路由和结果解析。
- OpenAPI 必须明确标记实际支持子集，不能继续展示不可执行的能力。
- 保存查询需要转换和不兼容状态展示。
- 旧客户端发送高级请求将从“旧引擎可执行”变为明确错误，这是有意的能力收缩。

## 迁移与回滚

在兼容转换器之前保留旧 decoder。切换按消费者进行，并保留短期 engine flag。若新引擎出现正确性问题，可以将受影响消费者路由回旧引擎，不修改客户端请求。

## 验证

- M0 固化每个消费者的请求/响应 fixture。
- M1 对兼容转换和 unsupported error 做协议测试。
- M4 对 V5 Result 做结构兼容测试。
- M6 使用真实认证请求覆盖全部目标消费者。

## 后续动作

- M0 完成后确定是否需要在响应 stats 中增加 engine/version 调试信息。
- M6 切换前制定旧保存查询的用户提示和迁移策略。
